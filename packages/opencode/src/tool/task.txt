Launch a new agent to handle complex, multistep tasks autonomously.

When using the Task tool, either specify subagent_type to launch a fresh specialized agent, or omit subagent_type to fork yourself with inherited conversation context. An implicit fork runs in the background by default and returns worker_id/task_id immediately.

When to use the Task tool:
- When you are instructed to execute custom slash commands. Use the Task tool with the slash command invocation as the entire prompt. The slash command can take arguments. For example: Task(description="Check the file", prompt="/check-file path/to/file.py")
- When you need parallel investigation or implementation while continuing your own work. Omit subagent_type to create a background fork that shares your context and can inspect or act independently inside a narrow directive.
- When you need a named specialist, specify subagent_type and provide a detailed autonomous task prompt.

When NOT to use the Task tool:
- If you want to read a specific file path, use the Read or Glob tool instead of the Task tool, to find the match more quickly
- If you are searching for a specific class definition like "class Foo", use the Glob tool instead, to find the match more quickly
- If you are searching for code within a specific file or set of 2-3 files, use the Read tool instead of the Task tool, to find the match more quickly
- Other tasks that are not related to the agent descriptions above


Usage notes:
1. Launch multiple agents concurrently whenever possible, to maximize performance; to do that, use a single message with multiple tool uses
2. To fork yourself, omit subagent_type. The fork inherits parent context, runs as a background teammate, must not spawn additional implicit forks, and should report only scoped findings. Do not read its transcript or wait on it unless its result is needed for your next step.
3. When the agent is done, it will return a single message back to you. The result returned by the agent is not visible to the user. To show the user the result, you should send a text message back to the user with a concise summary of the result. The output includes a task_id you can reuse later to continue the same subagent session.
4. Explicit subagents run in the background for asynchronous delegated work. They can perform generic delegated work directly, including research, edits, commands, tests, and verification when their permissions allow it. Background agents and implicit forks return a worker_id/task_id immediately and can receive follow-up instructions through the send_message tool. Plain text sent to a stopped background agent resumes it on the same task session. Set name when you want a stable human-readable target for send_message.
5. Prefer local background subagents by omitting isolation. Only set isolation="remote" when the user explicitly requested remote execution or a remote swarm endpoint is configured. Do not set cwd together with isolation; if you need a directory scope, put the path in the prompt or set cwd and omit isolation.
6. Set plan_mode_required=true or mode="plan" only for background agents that truly must inspect and propose a plan before making changes. Do not set plan mode just because the worker may edit files, run commands, or tests. Do not set plan mode for read-only research swarms unless the user explicitly wants approval gating. If the user asked for autonomous, YOLO, permission-free, or high-throughput swarm work, launch generic implementation workers without plan mode so they can do the assigned work directly. A plan-gated worker starts with mutating tools disabled, can still perform read-only inspection, sends a plan_approval_request to the team lead with send_message before mutations, and only receives edit/write/bash/apply_patch access after the lead sends a plan_approval_response approval. Use this for explicitly high-risk implementation swarms.
7. For coordinated swarm work, create a team with create_team, set team or team_name when launching related background agents, use create_task/update_task/get_task/list_team_tasks to maintain the team's shared task board, use broadcast to send the same coordination message to every active subagent in that team, and delete_team when the team is no longer needed. A lead session should manage one active team at a time.
8. Assign work by setting a shared task owner with update_task. Background team agents can also auto-claim pending unowned, unblocked tasks while idle. Agents should mark started work with update_task(status="in_progress") when needed, mark finished work with update_task(status="completed"), and use list_team_tasks after completing work to find newly unblocked tasks.
9. Use schedule_task for future follow-ups. Parent sessions can create durable schedules in .opencode/scheduled_tasks.json; live subagents can create session-only schedules routed back to themselves.
10. Use list_peers to discover same-project sessions and subagents addressable by send_message. Use session:<session_id> when you need to send a cross-session message to another opencode session.
11. Use list_teams to inspect teams. Use list_tasks to inspect running background agents, wait_task to wait for an agent to finish its current turn or block on permission, read_task_output to inspect a result/transcript, stop_task to stop a background agent, and cancel_task when you need explicit force-cancel semantics. Before delete_team, gracefully shut down active team members with shutdown_request messages; delete_team refuses active teams unless cancel_workers=true is explicitly passed for force cleanup.
12. New child sessions may inherit parent conversation context when needed, but the child is not the lead. Do not ask subagents to create/update goals, create/delete teams, manage other subagents, read other subagent transcripts, or spawn nested subagents. If a delegated task is self-contained, set context="fresh"; use context="fork" only when full parent context is genuinely needed. Provide task_id to resume the same subagent session, which continues with its previous messages and tool outputs. Your prompt should contain a highly detailed task description for the agent to perform autonomously and you should specify exactly what information the agent should return back to you.
13. The agent's outputs should generally be trusted
14. Clearly tell the agent whether you expect it to write code or just to do research (search, file reads, web fetches, etc.), since it is not aware of the user's intent. Tell it how to verify its work if possible (e.g., relevant test commands).
15. If the agent description mentions that it should be used proactively, then you should try your best to use it without the user having to ask for it first. Use your judgement.
